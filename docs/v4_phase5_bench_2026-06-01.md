## Notes on hot path

The merge step builds a `HashMap<DedupKey, MergedBondView>`
and inserts every (MemTable + L0 + v3) bond. For hub
subjects with high fan-out this allocates O(N) capacity;
if p99 inflates substantially under such subjects a
future port can swap to a subject-scoped `BTreeSet` or
a small-vec preallocator. Phase 5 keeps the simple
`HashMap` for clarity.

## Honest assessment vs the brief's 200 ns target

The brief projected `V4Only p50 ≤ V3Only + 50%` -- i.e. roughly 200 ns
against the Phase 0 v3 baseline (130 ns). The measured V4Only p50
is 310 µs, ~34x the local V3Only baseline (9.1 µs). The projection
was optimistic.

Where the time actually goes per V4Only read (with SST handles
cached):

1. `manifest.read().clone()` and L0 entry filter -- cheap, ~100 ns.
2. Per-L0 `find_block_for_subject` binary search -- 3 SSTs * ~200 ns = ~600 ns.
3. Per-L0 `decompress_block` (cache hit) + `parse_block` (zstd + bincode-ish parse) -- this is the dominant cost. Even with the block cache warm, the parsed `ParsedBlock` is reconstructed on every call because `parse_block` does not cache its output. 3 SSTs * ~100 µs = ~300 µs.
4. Linear scan over the block's CompactBonds for the subject match -- ~5 µs.
5. v3 heap `get_bond` x N neighbours -- ~1 µs.
6. HashMap dedup -- ~500 ns.

The optimisation that would actually move the needle is caching the
parsed-block layout (subject_table + bonds + keyframe_pool slice
view) instead of just the compressed bytes. That is a Phase 6
follow-up: leveled compaction wants the same per-SST cached layout
structure for the L1+ scans, so we land it once there and reuse.

For the spec's V3Only default, this overhead is INVISIBLE -- the
production binary still uses `read_outgoing_bonds_v3_only` which
is identical to today's v3 path. V4Only only matters in Phase 8
cutover; the parsed-block cache lands in Phase 6.

## Notes on hub-subject fan-out (brief's question)

For hub subjects the dedup HashMap allocates O(N) where N = sum of
outgoing bonds across all three layers. The cost is dominated by
fresh `MergedBondView::clone` (keyframe Vec clone, 1-3 keyframes
typical). At 1000-bond hubs this is roughly 10-50 µs of pure clone
overhead on top of the SST-read base cost. A subject-scoped BTreeSet
would not help because the underlying problem is the keyframe Vec
clone, not the set ops; a future port could switch keyframes to
`Arc<Vec<TemporalKeyframe>>` to share across views.
