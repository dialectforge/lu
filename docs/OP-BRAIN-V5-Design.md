## 1. Context & Motivation

v4 substrate (Phases 0–10.2) ships locally on `main` but failed three production cutovers (2026-06-01 night, 2026-06-02 early morning). Root cause per audit: Phase 2 chose block-local NodeIds in the SST format. That decision forced every cross-block subsystem (migration, verify, compaction) to maintain global Seed → NodeId mapping tables, which forced non-streaming implementations and HashMap-the-world antipatterns at production scale.

v3 production keeps working but is decaying. Ingest rate has dropped from 16.9 art/s → 6.3 art/s over recent weeks as brain grows. Wikipedia alone now projects ~8.5 months remaining. The save/dedup overhead scales with brain size — same ceiling that motivated v4 in the first place.

v5 substrate goal: streaming everywhere, bounded RSS as bonds grow, no per-pass HashMap-the-world for any cross-block operation.

## 2. Architectural Decisions

### Locked from audit

- **Brain-wide NodeIds** throughout. Use Phase 1's `NodeIntern` as the foundation.
- **Decoupled node storage from bond SSTs.** Separate node store with its own MemTable + WAL + flush + compaction. Bond SSTs reference NodeIds but do not carry node payloads.
- **Production-shape fixture FIRST.** Phase 0 builds a 5–10M record bench fixture and gates every subsequent phase on bounded-RSS assertions against it. No more 100K synthetic correctness tests that miss antipatterns.

### Decisions (locked 2026-06-08, revisions noted)

**Q1. NodeId encoding.** → **u64 with the high 32 bits reserved.** Current implementations write only the low 32 bits; readers MUST accept any value (forward-compat with future tenant / generation bits). On-disk varint encoding in WAL records and metadata, fixed-width u64 in CompactBond keys (see Q2). **No reuse on delete** — strictly append-only NodeId allocation. Deleted nodes get a tombstone marker in the node store; their NodeId never recycles. This kills an entire class of stale-pointer hazards. Confidence: HIGH.

**Q1 revision (Phase 0.a, 2026-06-08):** Current `NodeId` in `src/node_intern.rs:71` is `pub struct NodeId(pub u32);`. Phase 1 work is therefore a **u32 → u64 widening across all NodeIntern callers**, not just "add WAL persistence". Scope expands to: every site reading/writing NodeId, NodeIntern internal storage (HashMap key type), MemBond / SST writer signatures. A Phase 1.0 grep-and-list pass must enumerate the call sites before any code change so we sequence the widening cleanly.

**Q2. Bond SST key format.** → **Fixed-width 24-byte CompactBond keys** (8 + 8 + 8 for subject / predicate / object NodeIds). Primary sort order: `(subject, predicate, object)` to match the dominant typed_recall access pattern (subject → outgoing edges). **Secondary index SST** on `(object, predicate, subject)` for reverse traversal — built lazily during compaction, not maintained on every write. Block-level prefix compression recovers most of the size that varint would have saved without sacrificing random-access into SST blocks. 24 B/bond × 100M projected bonds = 2.4 GB (pre-compression). Confidence: MEDIUM — fixed-width vs varint is a real trade; revisit if SST size becomes the bottleneck. Current v4 `CompactBond` (`src/sst.rs:78-87`) is a 14-byte block-local struct (u32 subject_id/object_id indexing into per-block subject_table) — full rewrite.

**Q3. Node store SST format.** → **Primary node store sorted by NodeId** (canonical, source of truth for payloads). **Seed-hash → NodeId index** lives in `NodeIntern` (the v4 primitive), which is hot-cached in RAM and persisted as a **sidecar file (`nodeintern.bin`) inside the .lbr tar**, NOT embedded in the manifest rkyv blob. **Discipline note (Phase 0.a):** the current manifest (`src/manifest.rs:155-170` `ManifestPayload`) is a single rkyv blob written atomically via `save_atomic` at `manifest.rs:529`. At Q3's projected 2.4 GB / 100M-node NodeIntern, embedding inside the manifest is unworkable — Phase 1 implementation briefs must explicitly forbid the "just add a NodeIntern field to ManifestPayload" temptation. NodeIntern at 100M nodes — **revised by Phase 2.0 audit to ~8–9 GB resident**, not 2.4 GB (`HashMap<Seed, NodeId>` at 32+8 B × ~2× HashMap overhead = ~80 B/entry × 100M ≈ 8 GB, plus `Vec<Seed>` reverse map ~3 GB; original 24 B/node estimate underweighted HashMap overhead and the reverse map). Still fits the AX41-NVMe 64 GB budget but is now ~15% of available RAM (was projected 4%). Forward lookup is NodeIntern only; cold miss falls back to scanning the primary store by seed-hash secondary index (rare path). Confidence: MEDIUM — NodeIntern hot-cache size is the variable to watch as nodes grow.

**Q4. Migration story from v3.** → **Streaming v3 reader feeds v5 writer block-by-block** via a dedicated binary `lu_brain_migrate_v3_v5` (run-once, write-once). Bounded RSS target throughout migration: <2 GB. v3 brain.lbr is read-only during migration; v5 output writes to `/var/lib/lu/brain-v5/` alongside the live v3. **NO flag on lu_4_mcp** — separate binary, no risk of mixing migration code into the hot path. **Verification gate before any cutover:** post-migration read-back of N random bonds, total count match against v3, entropy spot-check against v3 hot-path query results.

**Q4 revision (Phase 0.a, 2026-06-08):** The audit's Appendix B claim that "v3 archive iteration is subject-sorted" was INCORRECT. `archive.rs:806 iter_bond_keys` returns `bond_index.keys().copied()` where `bond_index` is a `HashMap<(Seed, Seed), u32>` (both uncompressed `archive.rs:524` and compressed `compress.rs:1931` branches). HashMap iteration order is **not subject-sorted**. The migration tool therefore needs one of: (a) **external merge sort** of bond keys to disk during a Phase 7.0 "sort prep" stage with bounded RSS, (b) **bond-store SST writer that tolerates unsorted input** via in-memory merge buckets per range, or (c) **single-pass-with-buffering** that emits unsorted L0 SSTs and relies on compaction to sort. Recommendation: (a) — external merge sort with a streaming radix/bucket on-disk, bounded RSS <2 GB. (c) is tempting but pushes the sort work into compaction at first-boot of v5, which we don't want to gate cutover on. Confidence: HIGH that the constraint is real; MEDIUM on which of (a)/(b)/(c) is the right answer — Phase 7 design will pick this with bench data.

**Q5. Read path / MergedBondView with two stores.** → **Bond traversal uses NodeIds only.** Text resolution is a lazy lookup at the leaf of the call (when emitting results to the caller). NodeIntern is the single point of contact for ID↔text. `MergedBondView` dispatches across MemTable + L0..LN SSTs exclusively in the bond store — the node store is touched only for explicit Seed↔NodeId resolution at call boundaries. This is the streaming pattern v4 attempted but corrupted with block-local NodeIds. Phase 0.a confirms `src/read_path.rs` is pure types (no SST or node store references), and the actual merge lives in `brain.rs::read_outgoing_bonds_v4` (lines 10345-10440) which walks layers newest-first with a bounded per-subject HashMap — node-store lookup slots cleanly at leaf. Confidence: HIGH.

**Q6. Snapshot / v5enc archive format.** → **Single .lbr archive** at `/var/lib/lu/brain.lbr` (preserves v3's single-file mental model — matches DF security pinning, simpler backup/restore). **Internally a tar layout** with `node_store/`, `bond_store/`, `manifest`, `wal/`, `nodeintern.bin`. Snapshot writer streams the directory → tar → zstd → encrypt pipeline (no on-disk staging of the full archive). Snapshot reader does the reverse. Confidence: MEDIUM — single-archive ops simplicity is the right default; revisit if streaming becomes the bottleneck.

**Q7. Compaction interaction between stores.** → **Tombstone-based GC with epoch barriers.** Node store keeps tombstoned NodeIds until ALL bond store SSTs that could reference them have been compacted past the epoch barrier. Manifest tracks per-SST epoch. Node store compaction waits for the epoch barrier before discarding tombstones. Borrowed from RocksDB's snapshot-isolation pattern — simpler than full MVCC.

**Q7 revision (Phase 0.a, 2026-06-08):** Phase 0.a audit surfaced a SECOND HashMap-the-world in `src/compaction.rs:357` — `let mut rows: Vec<MergeRow> = Vec::new();` materializes ALL bonds from ALL input SSTs before sort/dedup. The audit memo Appendix F flagged only `node_winners` at line 362. The `rows: Vec` is the BIGGER memory hog at production scale. Q7's epoch-barrier compaction must replace BOTH the rows Vec AND the node_winners HashMap with a **streaming k-way merge over subject-sorted SST inputs**. The audit's salvage-shape claim for compaction.rs therefore covers the worker/scheduler scaffolding only — the merge loop is a full rewrite. Manifest's `last_compaction: i64` (single global timestamp at `manifest.rs:166`) must also extend to per-SST epoch in `SSTEntry`. Confidence: MEDIUM on epoch-barrier correctness — the principle is sound, the failure modes (epoch barrier deadlock, manifest corruption during simultaneous compaction) need careful test coverage in Phase 0 fixture.

**Q8. NodeIntern persistence in WAL.** → **Write-ahead ordering invariant:** NodeIntern record → bond record(s) → commit marker, all in the same WAL transaction. On replay, NodeIntern is reconstructed first, then bonds. NodeIntern is also snapshot-persisted as the `nodeintern.bin` sidecar (Q3, Q6) so cold restart loads sidecar + replays only WAL delta since last manifest. Phase 0.a confirms `src/wal.rs:168-169` already has a 1-byte record-type discriminator (`REC_TYPE_BOND=0`, `REC_TYPE_NODE=1`) — adding a `REC_TYPE_NODE_INTERN=2` is trivial. Confidence: HIGH — standard write-ahead semantics.

**Q9. Curiosity engine / K-gate / hub-fill compatibility.** → **All operate above the substrate via the `Brain` trait API. Substrate change is below the trait boundary.** No port required for K-gate, hub-fill, curiosity loop, thinking layer, narration, or extractor — they consume the Brain trait, which v5 will implement identically to v3. **Sanity check after Phase 5 (read path complete):** run K-gate self-test + hub-fill smoke test + curiosity wonder-queue probe against v5-backed Brain. If they pass, the rest carry over without source changes. Confidence: HIGH.

**Q10. Backwards compat / rollback path.** → **No v3 fallback compiled into v5 binary.** (v4's fallback masked bugs — exact pattern called out in feedback_no_hacks.) Cutover sequence: (1) migration tool emits `brain-v5/` alongside `brain.lbr`; (2) verification gate passes; (3) symlink swap + binary swap is the cutover; (4) 72-hour post-cutover monitoring window watching bounded-RSS + ingest-rate + recall-quality before declaring v5 production. **Rollback:** swap binary back to v3 md5 41f33466 + swap brain symlink back to brain.lbr. v3 brain is bit-preserved during migration (read-only). Rollback = 30-second operation. Confidence: HIGH.

## 5. Risk Register

- **Identifier-scope drift** — even with brain-wide NodeIds, future ports may introduce block-scoped indexes for perf. Audit at each phase.
- **NodeIntern manifest temptation** — Phase 1 implementers must NOT add a NodeIntern field to `ManifestPayload`. Q3 directive: sidecar file inside .lbr tar. Lockdown phrase for code review: "if it's in the manifest rkyv blob, it's wrong."
- **Migration data loss** — v3 brain at 18.6M bonds + 14 GB on disk represents months of training. Migration must be bit-exact and reversible. Verification gate (Q4) is the firewall. External sort prep (Phase 7.0) is required because v3 `iter_bond_keys` is HashMap-iter, not sorted.
- **Performance regression vs v3** — v3 ingest at 6.3 art/s is the floor; v5 must beat it and hold under brain growth. Phase 5 sanity check measures this.
- **Two-store coordination** — compaction overlap, snapshot consistency, replay ordering. Q7 epoch barrier is the discipline; Phase 0.c fixture must include concurrent-compaction failure-mode tests. Streaming k-way merge correctness is also gated here (Phase 0.a found a SECOND HashMap-the-world in compaction the audit missed).
- **Consumer-trait assumption** — "substrate change is below the Brain trait boundary" was WRONG for hub-fill, curiosity, and spread activation: they read the raw `AssociativeNetwork` adjacency (`network.bonds` / `network.nodes` / `neighbors_*` / `degree` / `get_bond`), not the Brain trait. Verified empirically at Phase 3.8; mitigated at Phase 3.8.1 via boot-time adjacency rehydration (Option A). Standing rule: any future architectural change that moves data from in-memory adjacency to substrate must enumerate and check EVERY adjacency reader, not just trait consumers.
- **NodeIntern memory growth** — Q3 hot-cache size at 100M nodes **≈ 8–9 GB resident** (Phase 2.0 audit revision — see SURPRISE-A in `docs/OP-BRAIN-V5-Phase2.0-NodeStore-Audit.md`). Now ~15% of AX41 64 GB budget. Revisit threshold rules before exceeding 50% of available RAM.

_3) Phase 3.7 bond-MemTable Seed-vs-NodeId gap_
- **What it is:** `MemBond` (`memtable.rs:54-57`) stores `object` as a **Seed**, not a NodeId (subject IS interned to NodeId — `BTreeMap<NodeId, Vec<MemBond>>` `:140`, `:209`). The v5 read path `get_outgoing_bonds_v5` is NodeId-in/NodeId-out and **SST-only** — its own doc-comment (`brain.rs:10897-10902`) states "the live MemTable bond half is NOT consulted (it stores objects as Seeds per audit Q3.0.F), so un-flushed bonds are invisible to this method until the next flush."
- **Why it blocks correct v5 load/read:** a freshly migrated brain has an empty MemTable, so a read-only cutover is momentarily fine. But the instant ingest/training resumes on v5, every new bond lands in the Seed-keyed MemTable and is **invisible to the NodeId-keyed `V5Only` read path until it flushes** → newly-learned facts silently un-recallable for a flush window. Flush already resolves objects Seed→NodeId at flush time (`flush.rs:498-512`: `intern.get(object_seed)` else `intern_or_get`), so the asymmetry is purely that the MemTable read seam never does this.
- **Recommendation (grounded in code): widen `MemBond` to carry the object NodeId at insert time** (option "c"). In `add_bond` (`memtable.rs:202-210`) intern the object Seed via `intern_or_get` alongside the already-interned subject, store the NodeId on `MemBond` (keep the Seed too if the v4 flush path still needs it during the 3.9 overlap, or drop it once v4 is gone). Then a `V5Only` read path merges MemTable + SSTs in one uniform NodeId key-space (same shadow/tombstone/seq rules as `rehydrate_adjacency`'s triple merge at `brain.rs:10113+`), and flush's object-intern branch becomes a no-op lookup. **Rejected alternatives:** _flush-before-switch alone_ is insufficient — it empties the MemTable once, but resumed ingest re-opens the gap immediately. _Read-time Seed→NodeId shim_ (intern objects on every read) works but adds per-read intern cost and keeps two key-spaces live; widening at insert is the same `intern_or_get` flush already pays, just moved earlier, and it's symmetric with how subjects/nodes are already handled. The Q3.0.F "keep objects as Seeds, NodeIds are block-local in the SST" rationale is about the **SST on-disk encoding** (block-local NodeIds), not the in-RAM MemTable — storing a brain-wide NodeId in `MemBond` does not conflict with it; flush still maps brain-wide→block-local when writing.

_4) ENCRYPTION — load-bearing finding: PLAINTEXT-AT-REST HOLE, and the guard silently passes it_
- Production v3 (`/var/lib/lu/brain.lbr`, 14 GB) is `v3enc` encrypted-at-rest (XOR-keystream per compressed block under master.key). `lu.service` runs with **`--require-encrypted`** + `--keyfile /var/lib/lu/master.key` (confirmed: `ExecStart=/usr/local/bin/lu_4_mcp --mcp --require-encrypted --keyfile /var/lib/lu/master.key --brain /var/lib/lu/brain.lbr --no-save`).
- **The v5 substrate is plaintext-on-disk by design, and the migration emits a plaintext directory — no encrypted outer archive exists.** NodeSST writer (`node_store/sst_writer.rs`) has NO key: `NodeSstWriteOpts` (`:199-207`) is `{target_entries_per_block, compression, file_uid}` only; the block format (`:26-31`) is `header + zstd|raw body` with no encrypt step. BondSST writer doc (`bond_store/sst_writer.rs:13-31`) states it explicitly: "Phase 3.1 ships plaintext-on-disk … `node_store/*.nsst` and `bond_store/*.bsst` are both plaintext inside the encrypted `.lbr` tar" — but **that outer encrypted `.lbr` tar is never built**: neither migration tool tars/seals/encrypts the output (grep: no tar/seal/wrap/`.lbr`-emit in either `migration_v3_v5_*.rs`); the bond tool's `key:Option<MasterKey>` (`:174-176`) is used ONLY to *decrypt the v3 source* (`open_v3_archive` `:409`), never to encrypt output. So a migrated v5 brain is a directory of plaintext SSTs leaking every KnowledgeNode payload (embeddings + subject text) and the full bond graph.
- **Worse — the guard is blind to it.** The `--require-encrypted` pre-load check `require_v3enc_or_err` (`brain.rs:248`) early-returns **`Ok(())` for ANY directory** (`:255-258`: `if path.is_dir() { return Ok(()); }`), with the comment "encryption is validated structurally by the v4 SST format + master.key." For **v4** dirs that was safe — v4 `L*-N.sst` are encrypt-then-compress when a key is supplied (`src/sst_writer.rs:40-68`). For **v5** dirs there is NO such structural validation and the SSTs are plaintext, so the production `--require-encrypted` config will load a plaintext v5 brain **silently, with no error** — directly violating the no-plaintext-brain-at-rest discipline (the same discipline that drove V1-JSON removal). This is the structural hole; the cutover MUST close it.
- **Recommended fix (Option B — per-SST encryption, restores v4 parity):** add `key: Option<MasterKey>` to `NodeSstWriteOpts` and `BondSstWriteOpts` and encrypt-then-compress each block exactly as the proven v4 `sst_writer.rs:40-68` XOR-keystream does (byte-position-equivariant, composes with zstd in either order). Thread the key: migration tools (already take `--keyfile`) pass it to the writers; `NodeFlushWorker`/`BondFlushWorker` already receive the key via `enable_flush_worker`/`enable_compaction` (`load_v4` passes `encryption_key`) — plumb into writer construction; `NodeSstReader`/`BondSstReader` + their caches gain a key and decrypt on read. **And fix `require_v3enc_or_err`** to actually validate a dir: require `manifest.master_key_id != KeyFingerprint::none()` and sniff an SST header's encrypted flag, erroring if a dir's stores are plaintext under `--require-encrypted`. Pros: no plaintext at rest ever; symmetric with the (already-proven) v4 scheme; no decrypt-to-tmp; readers still mmap individual files.
